# M1：运行内核如何保证并发安全

这一阶段把 AgentLoop 从“所有请求共用一把全局锁”改成了一个小型的、可控的调度器。一句话：**同一个 Session 按受理顺序串行，不同 Session 可以并行，Worker 用一个全局 Semaphore 限制真正进入 Provider 的主 Invocation 数量。**

## 1. 先统一入口，再谈并发

旧代码有两个入口：消息总线里的 `_dispatch`，以及 CLI/cron 使用的 `process_direct`。如果它们各自实现锁，很容易出现一条路径有顺序保证、另一条路径绕过保证的问题。

现在两条路径都进入 `_execute_entry`，然后依次经过 `_submit_invocation`、`_drain_session` 和 `_run_scheduled`。将来的服务 Worker 也应该调用这个入口。这样“读取历史、构造当前消息、执行 LLM 和 Tool、保存新一轮”都发生在同一个 Session 队首执行范围内，下一轮不会读到半写入的历史。

## 2. 为什么要按 Session 建队列

全局锁虽然简单，却把两个完全无关的聊天也排成一条队。现在 `_session_states` 以规范化后的有效 key 为索引，每个 key 有一个有界 `deque` 和一个 drain task。

提交时先计算 `ExecutionContext`。普通消息使用 `session_key_override` 或 `channel:chat_id`；system callback 则从 `chat_id` 中解析真实目标，例如 `telegram:42` 会归入 `telegram:42`。队列只接受这个最终 key，所以历史和工具路由不会落到错误 Session。

`_drain_session` 每次只取队首。一个 Session 的第二、第三个请求即使已经提交，也只能等待前一个请求完成；另一个 Session 有自己的 drain task，可以同时前进。队列和 `_pending_invocations` 都有上限，空队列完成后会删除状态，避免请求量增长时留下永久的锁对象。

## 3. Semaphore 为什么必须在队首才申请

Session 队列的等待不应该占用 Worker 执行额度。代码在 `_run_scheduled` 中先等待 `_execution_semaphore`，获得额度后才调用 `_process_message`。因此一个 Session 的大量积压不会提前把所有额度“借走”，其他 Session 仍能抢到额度；排队超时和执行超时也能分开记录。

`finally` 中无条件释放已经获得的 Semaphore。取消、Provider 异常和 `asyncio.wait_for` 超时都会经过这个路径。测试用 Event 控制 Provider 的进入和释放，不依赖“睡眠几秒后应该重叠”这种脆弱判断。

## 4. Invocation Context 和 Tool 隔离

`agent/execution.py` 定义了不可变的 `ExecutionContext`，并用 `contextvars` 保存当前 Invocation 的 Session、channel、chat、message 以及 request/trace/invocation ID。每次执行都会从注册表创建自己的 ToolRegistry。

MessageTool、SpawnTool、CronTool 都实现了 `clone_for_execution()`：

- MessageTool 的 channel、chat_id、message_id 和 `_sent_in_turn` 属于当前 Invocation；一个轮次已经通过 Tool 发送消息，不会让另一个轮次误判为已经发送。
- SpawnTool 把子任务绑定到规范化的 Session key，并由 SubagentManager 的总任务数和并发 Semaphore 限制后台资源。
- CronTool 只在当前 Invocation 副本上保存投递目标，不会被其他会话覆盖。

自定义 Tool 可以覆盖基类中的 `clone_for_execution()`，复制不可变依赖并重新创建自己的可变状态。默认的浅复制保留了旧的注入方式，适合无 per-invocation 状态的 Tool。

## 5. MCP 初始化为什么要共享 Task

MCP 连接是进程级资源，不能让两个 Invocation 同时初始化。`_connect_mcp` 在锁内只创建一个 `_mcp_init_task`，后来的调用等待同一个 Task；等待方被取消时使用 `shield`，不会顺便取消其他 Invocation 正在等待的初始化。初始化失败会清掉 Task，下一次调用可以重试。

## 6. 如何讲超时和取消

`accepted_at` 记录进入 Session 队列的时刻。`queue_timeout` 从这里开始，覆盖 Session 前序和 Semaphore 等待；成功获得 Semaphore 后才启动 `execution_timeout`。取消队列中的项目会把它移除并减少 pending 计数；取消正在执行的项目会取消隔离的 execution task，随后释放额度。测试最后检查 `_pending_invocations == 0`、Session 状态为空，并确认取消后下一轮仍能运行。

停机时先停止接收新 Invocation，再取消 drain 和 execution task；排队中的 future 也会被取消，避免 shutdown 之后又启动下一轮。

## 7. 后台能力和生命周期

M1 把 consolidation 放回 Session 队首内执行，并用 Worker 级长期记忆锁保护 workspace 级文件写入，避免后台任务和下一轮同时改 JSONL/记忆文件。Subagent 总数、并发数和 MessageBus 入站/出站队列都有上限。

`agents.runtime.enableConsolidation`、`enableSubagents`、`enableCron` 可以关闭尚未有服务级持久化生命周期的能力；Heartbeat 继续由 `gateway.heartbeat.enabled` 控制。服务模式在 M2/M3 接入 PostgreSQL、Outbox 和 Worker 生命周期前，建议关闭这些后台能力。CLI gateway 保留现有开关和行为。

## 8. 我会怎么展示回归证据

先运行聚焦测试确认顺序、重叠、Semaphore、Tool 归属、MCP 等行为，再运行完整旧测试确认 CLI 语义没有丢失。最后用 `scripts/m0_baseline.py` 的 Fake Provider 做入口探测：当前 bus 的不同 Session 会看到 `max_active=2`，同一 Session 的 direct 调用会看到 `max_active=1`。这是行为证据，不是性能数字。
